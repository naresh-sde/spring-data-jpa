# Spring Data JPA

Persistence layer done the production way — **entities, Spring Data repositories, derived + custom JPQL + native queries, relationships and pagination** (in-memory H2).

## Concepts covered

| Concept | Where |
|---------|-------|
| `@Entity`, `@Table`, `@Id`, `@GeneratedValue` | `model/Department.java`, `model/Employee.java` |
| `@Column` constraints (nullable, unique) | both entities |
| `@ManyToOne` + `@JoinColumn` (owns FK) | `Employee.department` |
| `@OneToMany(mappedBy)` (inverse) | `Department.employees` |
| `JpaRepository<Entity, Id>` | `repository/` |
| Derived query methods (parse method name) | `EmployeeRepository` (findBySalaryGreaterThan, ...) |
| `@Query` JPQL | `findInSalaryRange` |
| `@Query` native SQL | `findByDepartmentNameNative` |
| Pagination `Page<Employee>` + `PageRequest` (with `Sort`) | `getEmployeesByDepartment` |
| Optimistic locking `@Version` | `model/Employee.java` (`version` column) |
| Transactional service (`@Transactional`) | `service/impl/JpaServiceImpl.java` |
| H2 + `ddl-auto=none` + `schema.sql`/`data.sql` | `src/main/resources`, `application.properties` |

## Database Schema

The schema is **not** generated by Hibernate: `spring.jpa.hibernate.ddl-auto=none`, and
`src/main/resources/schema.sql` owns the DDL while `data.sql` owns the sample rows.
`spring.jpa.defer-datasource-initialization=true` makes both scripts run *after* Hibernate
starts (CommandLineRunner/DataSeeder then sees the rows).

### `departments`

| Column | Type | Null | Constraints |
|--------|------|------|-------------|
| `id` | `BIGINT` | no | **PK**, `AUTO_INCREMENT` (identity, `GenerationType.IDENTITY`) |
| `name` | `VARCHAR(100)` | no | **UNIQUE** (maps `@Column(nullable = false, unique = true)`) |
| `location` | `VARCHAR(150)` | yes | — |
| `created_at` | `TIMESTAMP` | yes | `DEFAULT CURRENT_TIMESTAMP` |

### `employees`

| Column | Type | Null | Constraints |
|--------|------|------|-------------|
| `id` | `BIGINT` | no | **PK**, `AUTO_INCREMENT` |
| `name` | `VARCHAR(100)` | no | — (`@Column(nullable = false)`) |
| `email` | `VARCHAR(150)` | no | **UNIQUE** (email is the business key — `findByEmail`, `existsByEmail`) |
| `salary` | `DECIMAL(12,2)` | no | — (drives `findBySalaryGreaterThan`, `findInSalaryRange`) |
| `joined_on` | `DATE` | yes | — (maps `Employee.joinedOn`, `LocalDate`) |
| `department_id` | `BIGINT` | no | **FK** → `departments(id)` via `fk_employees_department` |
| `version` | `BIGINT` | no | `DEFAULT 0`, mapped by `@Version` (optimistic locking) |
| `created_at` | `TIMESTAMP` | yes | `DEFAULT CURRENT_TIMESTAMP` |

### Relationship: department → employees (1:N)

One department has many employees, one employee belongs to exactly one department
(`department_id NOT NULL`):

```
departments (1) ──< employees (N)
     id  ◄── FK department_id
```

- Owning side: `Employee.department` — `@ManyToOne(fetch = EAGER, optional = false)` +
  `@JoinColumn(name = "department_id", nullable = false)`, so **the FK column lives on the child**.
- Inverse side: `Department.employees` — `@OneToMany(mappedBy = "department", cascade = ALL, fetch = LAZY)`;
  `mappedBy` must name the child field holding the FK, otherwise Hibernate tries to write a
  second `department_id` column.
- The native query joins the same FK: `select * from employees e join departments d on e.department_id = d.id`.

### Optimistic locking

`Employee.version` is annotated `@Version`: Hibernate adds `where id = ? and version = ?` to
every `UPDATE` and increments the column. If another transaction/thread updated the row in
between, the update affects 0 rows and Spring throws
`ObjectOptimisticLockingFailureException` (surfaced as a 500 ProblemDetail here) instead of
silently overwriting data. No locks are held, so concurrency stays high.

| 2 | HR | Pune |
| 3 | Sales | Mumbai |

`employees`:

| id | name | email | salary | joined_on | department_id |
|----|------|-------|--------|-----------|---------------|
| 1 | Asha | asha@engineering.com | 95000.00 | 2022-01-10 | 1 (Engineering) |
| 2 | Ravi | ravi@engineering.com | 78000.00 | 2023-03-01 | 1 (Engineering) |
| 3 | Meera | meera@hr.com | 62000.00 | 2021-06-15 | 2 (HR) |

The inserts use a subquery (`select id from departments where name = ...`) instead of hardcoding
ids, so H2's identity sequence stays in sync. `config/DataSeeder` is the JPA-based fallback: it
skips itself when `data.sql` already loaded rows, so the `UNIQUE` constraints are never violated.

## Run
```bash
mvn spring-boot:run
```
Seed data is loaded automatically by `schema.sql` + `data.sql` (3 departments, 3 employees).

```
POST /api/v1/departments                 {"name":"IT","location":"Hyderabad"}

GET  /api/v1/departments/{id}

POST /api/v1/employees                   {"name":"D","email":"d@x.com","salary":80000,"departmentId":1}
GET  /api/v1/employees/{id}
GET  /api/v1/departments/1/employees?page=0&size=5

```

## Key learning points
1. **Derived queries** = readable, no SQL ("findByDepartmentNameAndSalaryGreaterThan").
2. **@Query JPQL** — for complex queries JPQL works on entities (portable).
3. **nativeQuery = true** — raw SQL escapes, use only when necessary.
4. **Relations**: one side holds the FK (`@JoinColumn`), the other uses `mappedBy`. Careful with **lazy** collections — access them inside a transaction.
5. **Paging + sorting** via `Pageable` (see `PageRequest.of(page, size, Sort.by("name").ascending())`) avoids loading everything and lets the DB do the ORDER BY.
6. **Optimistic locking** with `@Version` — catches concurrent updates instead of losing them.
7. `dto` ↔ entity mapping keeps internal models decoupled from the API.
